## 🔎 Quick highlights from my findings

### Architecture & Purpose
- Event-driven TypeScript pipeline that:
  - Validates inputs, transforms data, publishes lifecycle events
  - Integrates with external APIs via `ApiClient` (Axios)
  - Supports batch processing with configurable concurrency and retry logic

### Core module interactions
- `DataProcessor` publishes events: `record.processing.started`, `record.processing.completed`, `record.processing.failed`.
- `EventBus` is the central publisher/subscriber with middleware and prioritized delivery.
- `DataProcessor` also subscribes to these events for logging / internal handling.

### Key implementation notes
- ApiClient retry implementation is in the response interceptor; it retries on: no response, HTTP 5xx, or 429, up to `retryAttempts`, with linear backoff (`retryDelay * attempt`).
- Validation (`validateDataRecord`) throws `ValidationError` — `DataProcessor` catches it, attempts retries, and publishes `record.processing.failed` once retries are exhausted.
- Concurrency handling uses `Promise.race` and an executing array — this is functional but fragile; better options exist.
- EventBus middleware transforms payloads before subscribers receive them.

### Debugging tips (events not received)
- Ensure subscriptions are added (`eventBus.getSubscriptions(...)`) and event type strings match exactly.
- Check middleware `eventBus.use` for throwing or corrupting payloads.
- Set `logger.setLevel(LogLevel.DEBUG)` to inspect emissions/handler logs.
- Confirm `EventBus.clear()` hasn't been called.

### Recommended improvements
- Implement exponential backoff and jitter for `ApiClient` retry handling; respect `Retry-After` header.
- Harden concurrency control (avoid removing promises by reference).
- Standardize and better structure error payloads and logging for tracing.
- Add tests for `ApiClient` retry and `EventBus` middleware/filters.
